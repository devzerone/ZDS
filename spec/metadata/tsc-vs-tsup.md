# `tsc` vs `tsup` 비교 메모

최종 업데이트: 2026-03-30

## 목적

이 문서는 현재 ZDS 패키지 빌드 구조에서 `tsc` 기반 빌드를 유지할지, `tsup`으로 전환할지를 빠르게 판단하기 위한 짧은 비교 메모입니다.

대상 패키지:

- `@zds/react`
- `@zds/tokens`

## 현재 상태

현재 레포는 다음 방식으로 빌드합니다.

- `@zds/react`: `tsc`로 `dist` JS와 선언 파일 생성
- `@zds/tokens`: `tsc` + JSON/CSS 복사 스크립트 조합

이 방식은 동작하지만, 설정과 보조 스크립트가 점점 늘어나는 경향이 있습니다.

## `tsc` 유지 시 장점

- TypeScript 표준 도구라 팀이 이해하기 쉽다
- 선언 파일 생성이 안정적이다
- 번들링이 없어 출력 구조를 예측하기 쉽다
- 라이브러리 내부를 있는 그대로 배포할 때 단순하다

## `tsc` 유지 시 단점

- 엔트리포인트가 늘수록 설정이 번거롭다
- JSON, CSS, 자산 복사는 별도 스크립트가 필요하다
- package export 구조와 build 구조를 수동으로 맞춰야 한다
- `paths`, `rootDir`, declaration 출력 문제를 직접 다뤄야 한다

## `tsup` 도입 시 장점

- 멀티 엔트리 라이브러리 빌드 구성이 단순하다
- ESM/CJS, 타입 선언, 아웃풋 경로를 한 곳에서 관리하기 쉽다
- `@zds/react` 같은 UI 라이브러리 패키지에 특히 잘 맞는다
- `tsc + 스크립트` 조합보다 설정 양을 줄이기 쉽다
- Turbo와 함께 써도 무난하다

## `tsup` 도입 시 단점

- 새 도구를 팀에 도입해야 한다
- 내부적으로 esbuild 기반이라 세부 출력 제어는 `tsc`와 감각이 다르다
- JSON/CSS/정적 자산은 여전히 일부 후처리가 필요할 수 있다
- 토큰 패키지처럼 코드와 데이터 산출물이 섞인 경우 완전한 대체는 아닐 수 있다

## ZDS 기준 판단

### `@zds/react`

`tsup` 적합도가 높습니다.

이유:

- 컴포넌트 엔트리가 앞으로 늘어날 가능성이 높음
- `index.ts`, `button.ts` 같은 엔트리 관리가 많아질 수 있음
- 라이브러리 빌드 도구로서 `tsup`의 장점이 바로 드러남

판단:

- `@zds/react`는 `tsup` 전환 가치가 큼

### `@zds/tokens`

`tsup` 적합도는 중간입니다.

이유:

- TS 엔트리 자체는 단순하지만
- 실제 핵심 산출물은 JSON 데이터와 CSS 생성물도 포함됨
- 따라서 `tsup`만으로 끝나기보다 복사/생성 후처리가 계속 필요함

판단:

- `@zds/tokens`는 `tsup`을 써도 되지만, 체감 이득은 `@zds/react`보다 작음

## 추천

가장 현실적인 선택은 다음 순서입니다.

1. 먼저 `@zds/react`만 `tsup`으로 전환
2. `@zds/tokens`는 당분간 현재 방식 유지
3. 필요해지면 나중에 `tsup + copy/generate` 구조로 확장 검토

## 한 줄 결론

이 레포에서는 `tsup`이 특히 `@zds/react`에 유리하고, `@zds/tokens`에는 선택적입니다.
