# Feature Specification: 브레드크럼프 컴포넌트

**Feature Branch**: `006-breadcrumb-component`  
**Created**: 2026-03-31

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 현재 위치를 빠르게 파악 (Priority: P1)

사용자와 제품팀은 계층형 정보 구조를 가진 화면에서 지금 어디에 있는지 빠르게 이해하고, 상위 단계로 안전하게 돌아갈 수 있는 공통 브레드크럼프를 원한다. 이 컴포넌트는 페이지 제목만으로는 부족한 맥락을 보완해 탐색 부담을 줄여야 한다.

**Why this priority**: 브레드크럼프의 가장 핵심 가치는 현재 위치와 상위 경로를 즉시 드러내는 것이다. 이 기준이 먼저 정리되어야 이후 스타일이나 문서보다 실제 사용 가치가 성립한다.

**Independent Test**: 검토자는 브레드크럼프만 보고 현재 화면의 계층 위치와 돌아갈 수 있는 상위 단계들을 이해할 수 있어야 하며, 마지막 항목이 현재 위치라는 점을 일관되게 식별할 수 있어야 한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 다단계 탐색 구조 안의 상세 화면에 도착한 상태에서, **When** 브레드크럼프를 확인하면, **Then** 현재 화면까지의 상위 경로를 순서대로 이해할 수 있어야 한다.
2. **Given** 사용자가 상위 단계로 되돌아가고 싶은 상태에서, **When** 브레드크럼프의 이전 단계 항목을 보면, **Then** 돌아갈 수 있는 목적지를 명확히 구분할 수 있어야 한다.

---

### User Story 2 - 일관된 항목 구성과 길이 처리 사용 (Priority: P2)

디자이너와 프론트엔드 엔지니어는 브레드크럼프가 다양한 깊이와 긴 레이블을 가진 화면에서도 일관된 항목 구조, 구분자 표현, 마지막 항목 규칙을 유지하길 원한다. 그래야 화면마다 다른 탐색 표시를 임의로 만들지 않고도 재사용할 수 있다.

**Why this priority**: 실제 제품에서는 정보 구조 깊이와 레이블 길이가 제각각이라서, 항목 규칙과 길이 대응 원칙이 없으면 같은 컴포넌트라도 화면별 품질 차이가 커진다.

**Independent Test**: 검토자는 얕은 경로, 깊은 경로, 긴 레이블 경로 예시를 비교했을 때 어떤 항목이 링크 가능하고 어떤 항목이 현재 위치인지 일관되게 설명할 수 있어야 한다.

**Acceptance Scenarios**:

1. **Given** 브레드크럼프가 여러 단계의 경로를 표시하는 상태에서, **When** 사용자가 항목을 확인하면, **Then** 각 단계는 동일한 순서 구조와 구분 규칙으로 표현되어야 한다.
2. **Given** 일부 단계 레이블이 길거나 경로 깊이가 깊은 상태에서, **When** 브레드크럼프가 표시되면, **Then** 현재 위치 인지성과 상위 단계 구분이 유지되어야 한다.

---

### User Story 3 - 접근 가능한 탐색 보조 수단 제공 (Priority: P3)

접근성 리뷰어와 구현 담당자는 브레드크럼프가 시각적 장식이 아니라 탐색 보조 수단으로 인식되기를 원한다. 키보드 사용자와 보조 기술 사용자도 현재 위치와 이동 가능한 단계들을 혼동 없이 이해할 수 있어야 한다.

**Why this priority**: 브레드크럼프는 탐색 구조를 설명하는 요소이므로 접근 가능한 의미 전달이 빠지면 컴포넌트 가이드의 완성도가 크게 떨어진다.

**Independent Test**: 검토자는 키보드 탐색과 보조 기술 읽기 순서를 기준으로 브레드크럼프를 점검했을 때, 현재 위치와 이동 가능한 항목이 서로 다른 의미로 전달된다고 판단할 수 있어야 한다.

**Acceptance Scenarios**:

1. **Given** 키보드 사용자가 브레드크럼프를 탐색하는 상태에서, **When** 링크 가능한 항목에 순차적으로 접근하면, **Then** 현재 위치가 아닌 단계들만 이동 가능한 대상으로 인식되어야 한다.
2. **Given** 보조 기술 사용자가 브레드크럼프를 읽는 상태에서, **When** 현재 위치 항목에 도달하면, **Then** 해당 항목이 이동 대상이 아니라 현재 위치라는 의미로 전달되어야 한다.

### Edge Cases

- 브레드크럼프가 한 단계만 있는 경우에도 현재 위치를 중복되거나 어색하게 표현하지 않아야 한다.
- 경로 단계 수가 많아 화면 폭이 제한될 때도 시작점, 현재 위치, 축약 여부가 혼동 없이 드러나야 한다.
- 중간 단계의 레이블이 매우 길더라도 마지막 항목과 링크 가능 항목의 구분은 유지되어야 한다.
- 일부 상위 단계가 현재 세션에서 이동 불가능한 경우에도 항목 의미와 비이동 상태가 명확히 구분되어야 한다.
- 구분자 자체는 탐색 목적지가 아니므로 항목과 같은 상호작용 대상으로 오인되지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 계층형 탐색 경로를 순서대로 표시하는 공통 브레드크럼프 컴포넌트를 제공해야 한다.
- **FR-002**: 시스템은 브레드크럼프의 각 단계가 레이블을 가져야 하며, 마지막 단계를 현재 위치로 취급해야 한다.
- **FR-003**: 사용자는 마지막 단계를 제외한 이전 단계들을 상위 경로 이동 후보로 인식할 수 있어야 한다.
- **FR-004**: 시스템은 링크 가능한 단계와 현재 위치 단계를 시각적으로 구분할 수 있어야 한다.
- **FR-005**: 시스템은 브레드크럼프 단계 사이에 순서를 드러내는 구분 표현을 제공해야 한다.
- **FR-006**: 시스템은 브레드크럼프가 한 단계 경로와 다단계 경로 모두를 일관된 규칙으로 표시해야 한다.
- **FR-007**: 시스템은 긴 레이블이나 깊은 경로에서도 시작점과 현재 위치의 인지성을 유지해야 한다.
- **FR-008**: 시스템은 경로 축약 또는 길이 제약이 적용되는 경우에도 현재 위치와 되돌아갈 수 있는 핵심 단계가 유지되도록 정의해야 한다.
- **FR-009**: 시스템은 현재 위치 단계가 이동 가능한 링크처럼 오인되지 않도록 해야 한다.
- **FR-010**: 시스템은 구분 표현이 항목 레이블보다 우선적으로 읽히거나 상호작용 대상으로 해석되지 않도록 해야 한다.
- **FR-011**: 시스템은 키보드 사용자에게 이동 가능한 단계만 탐색 대상으로 제공해야 한다.
- **FR-012**: 시스템은 보조 기술 사용자에게 브레드크럼프가 탐색 경로이며 마지막 항목이 현재 위치임을 전달해야 한다.
- **FR-013**: 시스템은 기본 브레드크럼프, 긴 경로 대응, 비이동 현재 위치 규칙을 문서와 예시에서 함께 설명해야 한다.
- **FR-014**: 시스템은 디자인 산출물, 구현 산출물, 문서에서 동일한 단계 의미와 명명 규칙을 재사용할 수 있어야 한다.
- **FR-015**: 시스템은 이번 범위에서 계층 탐색 보조에 필요한 기본 브레드크럼프만 다루며, 드롭다운이 결합된 복합 네비게이션 패턴은 제외해야 한다.

## Artifact Impact & Parity *(mandatory)*

### Source-of-Truth Updates

- **Spec Artifacts**: `spec/components/breadcrumb/breadcrumb.spec.json` 신규 생성
- **Token / Foundation Artifacts**: `packages/tokens/data/components/breadcrumb.json` 신규 생성 또는 공통 탐색 계열 토큰 참조 보강, 필요 시 `packages/foundation/`의 navigation usage guidance 보완
- **Pencil Baselines**: `pen/components/breadcrumb/breadcrumb.pen` 신규 생성

### Delivery Surface Updates

- **Implementation Packages**: `packages/react/src/primitives/breadcrumb/`, `packages/react/src/components/breadcrumb/`
- **Docs / Preview Surfaces**: `apps/docs/content/components/breadcrumb.mdx`, `apps/docs/app/components/breadcrumb/page.tsx`, `.storybook/`와 연결되는 breadcrumb story surface
- **Validation Artifacts**: `testing/spec/validate-breadcrumb-spec.mjs`, `testing/accessibility/breadcrumb-accessibility-checklist.md`, `testing/visual/breadcrumb-visual-checklist.md`

### Platform Parity & Exceptions

- **Parity Impact**: 이번 기능은 React를 기준선으로 하는 첫 브레드크럼프 계약을 정의하며, 후속 플랫폼 확장을 위한 공통 의미와 예외 기록의 출발점을 만든다.
- **Approved Exceptions**: 초기 범위에서는 React 외 플랫폼 구현은 포함하지 않으며, 해당 플랫폼들은 `not-started` 상태로 기록한다.
- **Parity Metadata Location**: 브레드크럼프 parity 메타데이터의 canonical 위치는 `spec/components/breadcrumb/breadcrumb.spec.json`이다.
- **Primitive / Headless Strategy**: React에서는 저수준 상호작용과 의미 구조를 `primitives`에 두고, 공개 사용 API와 토큰화된 표현은 `components`에서 제공한다. 기본 의미 전달은 가능한 한 네이티브 탐색 구조를 우선 활용한다.

### Key Entities *(include if feature involves data)*

- **브레드크럼프 항목**: 계층 경로의 한 단계를 나타내는 단위. 레이블, 현재 위치 여부, 이동 가능 여부 같은 의미 속성을 가진다.
- **브레드크럼프 경로**: 시작점부터 현재 위치까지 이어지는 순서형 단계 집합이다.
- **구분 표현**: 단계 사이의 순서를 보여주는 시각적 보조 요소다. 항목 의미를 보완하지만 독립 목적지는 아니다.
- **축약된 경로 표현**: 경로 길이 제한이 있을 때 일부 중간 단계를 요약해 현재 위치 인지성을 유지하는 표시 방식이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 검토 참가자 5명 중 최소 4명은 브레드크럼프 예시를 보고 10초 이내에 현재 위치 항목을 올바르게 식별할 수 있어야 한다.
- **SC-002**: 검토 참가자 5명 중 최소 4명은 다단계 예시를 보고 첫 시도에 이동 가능한 상위 단계와 현재 위치 단계를 구분할 수 있어야 한다.
- **SC-003**: 신규 팀원은 브레드크럼프 문서를 검토한 뒤 15분 이내에 한 단계 경로, 일반 경로, 긴 경로 대응 규칙의 차이를 설명할 수 있어야 한다.
- **SC-004**: 접근성 검토에서 키보드 탐색 시 이동 가능한 단계만 순차 탐색 대상으로 노출되고, 현재 위치는 이동 대상으로 오인되지 않아야 한다.
- **SC-005**: 문서와 시각 기준선을 함께 본 검토자는 기본 브레드크럼프와 길이 제약 대응 예시에서 단계 순서와 현재 위치 의미를 일관되게 해석할 수 있어야 한다.

## Assumptions

- 첫 번째 버전은 페이지 내 계층 탐색을 보조하는 기본 브레드크럼프 계약, 시각 기준, 문서, React 구현을 다루며 복합 메뉴 결합 패턴은 후속 작업으로 분리한다.
- 브레드크럼프는 기존 토큰 체계를 소비하는 navigation 계열 컴포넌트로 간주하며, 전용 브랜드 색 체계를 새로 정의하지 않는다.
- 사용자는 문서 사이트, 관리자 화면, 설정 화면처럼 다단계 정보 구조를 가진 제품 화면에서 브레드크럼프를 주로 사용한다.
- 현재 위치는 항상 경로의 마지막 단계이며, 마지막 단계의 의미는 링크 가능 단계와 구분되어야 한다.
- 경로 길이 제약이 있는 경우에도 시작점과 현재 위치는 가능한 한 유지하는 방향을 기본 원칙으로 삼는다.
- 후속 플랫폼 parity 작업 전까지는 React 구현과 관련 문서가 공식 기준선 역할을 한다.
